# 01 — Shared Contracts and Data Model

This is the **frozen contract** all four teams build against. It expands the Project Doc's §3 ("Cross-Team Interface Standards") with the field-level detail agents need and cannot guess. Nothing here contradicts the Project Doc; where the Project Doc already gives a rule (envelope shape, header list, state sequence), it is referenced, not re-explained.

Any change to this document requires sign-off from the project lead and every affected team lead. Coding agents must not alter it.

## 1.1 Transport rules **[PROJECT DOC]**

Reuse the Project Doc §3.1 header table and §3.2 response envelopes exactly:
- `Authorization`, `X-Correlation-ID`, `Idempotency-Key`, `X-API-Version`, `Content-Type: application/json; UTF-8`, ISO-8601 UTC timestamps, opaque string/UUID identifiers.
- Success/error envelope shapes as given.

Additions **[SPEC]**:

- **Correlation ID format:** UUID v4 string. Generated by Team D at the start of a user-facing flow, or by Team C when it originates an internal call. Every service must propagate the *same* value unchanged through every downstream call and log line for that flow — never regenerate it partway through.
- **Idempotency-Key scope:** unique per (endpoint, key) pair. A producer must persist the first response for a key and return that identical response — same status code, same body — on any retry with the same key, for at least 24 hours (demo-scope retention).
- **Clock skew:** all services should trust their own local clock; no NTP-sync requirement for this scope.

## 1.2 Error code registry **[SPEC]**

The Project Doc shows one example (`RULE_CONFLICT`). Teams need a shared, closed vocabulary so Team D can render errors without team-specific branching. Owners may add codes for internal-only errors, but every **cross-team** error must use one of these:

| Code | HTTP status | Meaning | Typical owner |
| --- | --- | --- | --- |
| `VALIDATION_ERROR` | 400 | Request failed schema/field validation | Any |
| `UNAUTHORIZED` | 401 | Missing/invalid credential | Any |
| `FORBIDDEN` | 403 | Authenticated but not permitted for this action | Any |
| `NOT_FOUND` | 404 | Referenced entity does not exist | Any |
| `IDEMPOTENCY_CONFLICT` | 409 | Same key reused with a different request body | Team C |
| `RULE_CONFLICT` | 409 | Eligibility rule chain rejected the request | Team A |
| `STATE_CONFLICT` | 409 | Requested transition invalid from current state | Team C |
| `VERSION_MISMATCH` | 409 | `graph_version` / application `version` stale | Team B / Team C |
| `SLOT_UNAVAILABLE` | 409 | Interview slot/seat exhausted | Team A / Team C |
| `LOCK_TIMEOUT` | 423 | Could not acquire a required lock in time | Team A / Team C |
| `RATE_LIMITED` | 429 | Caller exceeded agreed rate limit | Any |
| `UPSTREAM_UNAVAILABLE` | 502 | A dependency (A, B, or C) failed or timed out | Team C / Team D |
| `INTERNAL_ERROR` | 500 | Unhandled fault | Any |

Every error's `details` array should contain machine-checkable entries (e.g. `{"field": "cgpa", "reason": "below_cutoff"}`), not just prose, so Team D can build the "100% error classes map to a clear action" KPI without hardcoding per-message text.

## 1.3 Cross-team data objects — expanded schema **[SPEC]**

The Project Doc's §3.3 table gives *minimum fields* only. Below is the full field-level shape agents should implement. Fields not listed here but needed internally by a team are that team's own concern and are **not** part of the shared contract (don't expose them cross-team).

### ApplicationRequest / Application (owner: Team C)
```
application_id      string (UUID)              server-generated
student_id          string                     required
drive_id            string                     required
resume_version      string                     required
consent             boolean                    required, must be true to proceed
idempotency_key     string                     required (header, echoed in audit)
state                enum (see §1.4)            server-managed
version              integer, starts at 1        optimistic-concurrency token
decision_id           string | null              set once Team A responds
ranking_id            string | null              set once Team B responds
created_at / updated_at   ISO-8601 timestamp
```

### EligibilityRequest (owner: Team A)
```
request_id           string (UUID)   server-generated by Team A
application_id        string          from Team C
student_id             string
drive_id                string
rule_set_version        string          which rule set to evaluate against
priority                 enum: NORMAL | HIGH
submitted_at              ISO-8601
```

### EligibilityDecision (owner: Team A)
```
decision_id           string (UUID)
request_id             string
eligibility_result      enum: ELIGIBLE | CONDITIONAL | NOT_ELIGIBLE
failed_rules              array<string>     rule codes that failed, [] if ELIGIBLE
rule_set_version           string
lease_id                    string | null     set if an interview slot was reserved
decision_metrics              object            { evaluation_time_ms, queue_wait_ms }
```

### RankingRequest (owner: Team B)
```
ranking_id_request     string (UUID)
drive_id                 string
graph_version              string             version of the skill/requirement graph used
algorithm                    enum: WEIGHTED_SCORE | HEAP_TOPK | MERGE_SORT
constraints                    object             free-form, algorithm-specific
```

### RankingResult (owner: Team B)
```
ranking_id              string (UUID)
ordered_candidates        array<{student_id, score, rank}>
total_score                 number
algorithm                     string
graph_version                  string
tie_break_rule                  string
explored_candidate_count          integer
```

### Drive (owner: Team C)
```
drive_id           string (UUID)
company            string
criteria             object   { min_cgpa, max_backlogs, allowed_branches[], min_attendance, required_skill_tags[] }
seats                integer
package               string   (display string; not parsed for logic)
state                  enum: DRAFT | OPEN | CLOSED | ARCHIVED
version                 integer
```

### DashboardAggregate (owner: Team D, assembled from A/B/C)
```
application       object   (Team C Application, trimmed for the viewer's role)
decision            object   (Team A EligibilityDecision, if present)
ranking               object   (Team B RankingResult, if present)
freshness               ISO-8601   timestamp of the most recent contributing update
alerts                    array<string>
permissions                 array<string>   what actions the current viewer may take
```

## 1.4 Application state machine — full transition table **[SPEC]**

The Project Doc gives the happy-path sequence and names the alternative outcomes but not the legal transition graph. Team C is the sole writer of `state`; this table is what Team C's state-machine service must enforce (and what Team C's tests in §"minimum test scenarios" verify).

| From | Allowed next states |
| --- | --- |
| *(new)* | `APPLIED` |
| `APPLIED` | `SCREENING`, `WITHDRAWN` |
| `SCREENING` | `RULE_EVALUATED`, `WITHDRAWN`, `EXPIRED` |
| `RULE_EVALUATED` | `SHORTLISTED`, `NOT_ELIGIBLE`, `WAITLISTED`, `WITHDRAWN` |
| `SHORTLISTED` | `INTERVIEW_SCHEDULED`, `WAITLISTED`, `WITHDRAWN`, `COMPENSATION_REQUIRED` |
| `INTERVIEW_SCHEDULED` | `SELECTED`, `WAITLISTED`, `WITHDRAWN`, `COMPENSATION_REQUIRED` |
| `SELECTED` | `OFFER_ISSUED`, `COMPENSATION_REQUIRED` |
| `OFFER_ISSUED` | *(terminal)* |
| `NOT_ELIGIBLE` | *(terminal)* |
| `WAITLISTED` | `SHORTLISTED`, `EXPIRED`, `WITHDRAWN` |
| `WITHDRAWN` | *(terminal)* |
| `EXPIRED` | *(terminal)* |
| `COMPENSATION_REQUIRED` | *(re-enters the state it failed from, after compensation completes; never exposed as a resting state beyond that transaction)* |

Any transition not listed is illegal and must be rejected with `STATE_CONFLICT`. This table is what "0 illegal transitions" in the Project Doc's E2E KPI table is measured against.

## 1.5 Versioning policy **[PROJECT DOC + SPEC]**

- URI-based versioning (`/api/v1/...`) is primary, per the Project Doc.
- Additive changes (new optional field, new enum value that old consumers can ignore) do not require a version bump but must be announced to all consumers before merging.
- Breaking changes (removed/renamed field, stricter validation, changed status code) require a new `/v2` path or an agreed deprecation window, per the Project Doc §7.1. **No team may silently ship a breaking change to a `/v1` contract.**
- `graph_version` (Team B) and application `version` (Team C) are optimistic-concurrency tokens, not API versions — don't conflate them with `X-API-Version`.
