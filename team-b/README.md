# Team B — Ranking & Analytics Engine

Team B owns its in-memory candidate graph, eligibility/ranking (B1/B2), shortlist retrieval (B3), and historical placement aggregation (B4). Team C remains the authoritative application and placement state store; Team B consumes supplied API data and does not access Team C's database.

Team C integration is pending: the sibling `team-c/src/server.ts` currently contains only a startup stub and exposes no service contract for Team B to call. No fake integration endpoint is used.

## B3: shortlist lookup

On replacement, B3 removes candidate keys no longer present and refreshes each retained or added entry with its new rank, score, and profile version. Matching cache invalidation removes that shortlist's index entries; entries for other shortlists remain. Every cache read now requires an expected profile version.

B3 indexes B2's existing ordered shortlist output; it does not rank candidates. Entries retain the B2 fields `student_id`, `rank`, and `score`. The lookup `key` is a candidate index key formed as URL-encoded `shortlist_key::student_id`; this lets a student appear in multiple shortlists without overwriting another index entry. Index entries point to their shortlist cache key. The response's `cached_shortlist` object contains an `entries` array of ordered B2 entries. `index_statistics` reports entry, lookup, hit, and miss counts. Profile-version mismatch and expiry remove or refuse the stale cache value. Invalidation is conditional on an exact `profile_version`, so a request for an older version cannot delete a newer entry. Hash map lookup is average O(1), not guaranteed O(1); AVL search/insert/delete are O(log n). Both index implementations are in-memory processing representations.

AVL is the chosen balanced-tree variant alongside Hash. A Red-Black Tree is not added because the requirement permits AVL or Red-Black Tree, and duplicating a second balanced tree would not add a required capability.

The API server in `src/api/server.ts` binds these operations to HTTP routes and uses the shared `{data, meta}` / `{error, meta}` envelope. The metrics route reports observed cache hit rate and index lookup p95. Ranking computation latency is measured by the reproducible benchmark command below.

## B1: profile coverage

`GET /api/v1/profiles` includes `graph.coverage_summary`. `total_student_skill_edges` and `total_drive_skill_edges` count distinct student-skill and drive-required-skill graph edges. Coverage is measured over distinct `(drive_id, required_skill)` pairs: a pair is covered when at least one registered student has that skill. `covered_required_skill_pairs`, `uncovered_required_skill_pairs`, `coverage_percentage`, and the sorted `uncovered_requirements` list report that result. With no drive-required-skill pairs, coverage percentage is 0 because there is no denominator. Existing graph version, student count, and drive count remain in the graph summary.

## B2: ranking request options

`POST /api/v1/rankings/compute` accepts `candidate_pool`, `optimization_metric`, and `constraints`. Omitting `candidate_pool` considers all registered students. A supplied pool is deduplicated and sorted; unknown IDs reject the request with validation error, and an empty pool returns an empty ranking with `explored_candidate_count: 0`. The count is the number of unique known pool members considered before eligibility/constraint filtering. Ranking IDs include effective HEAP_TOPK K, candidate pool, and constraints so distinct results are stored separately.

Only `SCORE_DESC` is supported for `optimization_metric`; it maximizes the existing weighted score, with the existing CGPA and student-ID tie-breaks. Supported constraints are `min_cgpa` (tightens the drive cutoff), `max_backlogs` (tightens the drive limit), and finite `min_project_score`. Unsupported constraint names or invalid values are rejected. Drive branch, attendance, required-skill, and cutoff eligibility rules continue to apply. No other optimization metric or constraint is silently ignored.

## B4: historical placement analytics

Under the current MVP buckets, **zero LPA is valid** and belongs to `[0,3)`. Changing that rule would move zero-valued placed records to `missing_or_invalid` and requires an explicit decision. The service adapters validate invalidation body field types, analytics filter types, and supplied UUID v4 correlation IDs; invalid analytics filters and correlation IDs raise `TypeError` for the host HTTP layer to map. The host must still enforce required headers and HTTP status mapping.

The MVP record is `{student_id, department, batch, company, stage, package_lpa?}` with stage `Applied | Eligible | Shortlisted | Placed`. The company/student pair is the deduplication key because placement cycle is not a field. Duplicate rows keep the most advanced explicitly observed stage; duplicate placed rows use the lowest valid package so a repeated record cannot inflate a count. Filters are applied before deduplication and aggregation. Conflicting department/batch values within duplicates should be corrected at the input source; cycle-level distinctions cannot be expressed by this model.

B4 reports both a pooled `conversion_rate` and a deterministic, company-key-sorted `company_conversion` map with distinct applied and placed student counts and each company's conversion rate.

`department_trend` is an object keyed by URL-encoded `department::batch` and groups by department and batch. Its rate is distinct placed students / distinct represented students in that cohort × 100. `conversion_rate` pools company applications after filtering: distinct placed student-company pairs / distinct applied student-company pairs × 100; any valid stage represents an application. A student applying to two companies contributes two company applications. Package ranges are `[0,3)`, `[3,6)`, `[6,10)`, and `[10,+∞)` LPA. Missing, negative, NaN, or infinite packages on placed records are counted in `missing_or_invalid`, never coerced to zero. Only placed rows contribute to package buckets.

Aggregation takes O(n + c log c): one pass over n records plus sorting c distinct cohorts for stable output. Analytics are historical summaries only and do not perform current candidate ranking. Runtime benchmarks are reported separately from placement metrics.

The analytics request accepts only `algorithm: "DETERMINISTIC_AGGREGATION"`. `repetitions` defaults to 1 and must be an integer from 1 through 100; each repetition aggregates the same supplied snapshot, and the response reports selected algorithm, actual `benchmark_size`, repetition count, total elapsed time, and average duration. Optional `benchmark_size` must be an integer from 0 through 1,000,000 and equal the supplied record count. The analytics result remains deterministic; timing fields are measurements and vary by run.

## Reproducible benchmarks

Run `npm run benchmark` to execute the ranking, shortlist index, cache, invalidation, and local ranking API load benchmarks. The command builds the TypeScript project and runs `src/demo/benchmarkDemo.ts`.

The ranking benchmark generates 1,000 deterministic student profiles and a graph with 5,000 edges, warms each supported algorithm, then reports per-algorithm p50/p95/p99, min, max, and mean elapsed milliseconds over the requested repetitions. Full-result comparisons use K=1,000 for all algorithms. A separate configurable HEAP_TOPK workload defaults to K=10 and reports its K, result count, and timing distribution. HEAP_TOPK ranking IDs include the effective returned K so distinct shortlist results can be retrieved independently. It compares full-result MERGE_SORT and HEAP_TOPK scores and ordering with WEIGHTED_SCORE, reporting score deviation, candidate discrepancy, and ordering mismatches. If candidates are missing, `max_score_deviation` is `null` and `has_discrepancy` is true; JSON does not silently convert infinity to null. The benchmark reference is the WEIGHTED_SCORE output from the same implementation; this is an in-project consistency check, not an independent external oracle. A separate B2 test defines a small hand-calculated cohort independently of the scoring function; it verifies that cohort but does not establish correctness for every reference cohort.

The Hash/AVL benchmark runs the existing `ShortlistIndex` implementations over 10,000 entries and 20,000 deterministic hit/miss lookups. It reports total, average, p50, and p95 lookup timings. Structural counts describe logical Map entries and AVL nodes, not RAM usage; each current `ShortlistIndex` instance maintains both structures. Latency is measured directly; exact per-structure RAM is not claimed because JavaScript object sizes are not measured reliably here. Expected lookup complexity is average O(1) for Map and O(log n) for AVL.

The cache benchmark performs repeated reads of a computed shortlist with a deterministic 90% intended hit pattern and measures actual hit/miss counts, then measures individual invalidation durations. A hit rate of 90% applies only to this deterministic benchmark workload, not production traffic.

The API benchmark performs 20 warm-up requests, then 3 measured runs of 400 requests each, scheduled toward 200 requests per second on an in-process HTTP server using the actual ranking route. Each run reports the target rate, scheduled and dispatched counts, client dispatch rate calculated from actual dispatch timestamps over the first-to-last dispatch interval, response success/failure percentage, response throughput (received HTTP responses per second from first dispatch to last received response), and latency p50/p95/p99. The dispatch and response windows exclude server startup and shutdown. Response drain is included in response throughput but not dispatch rate. Dispatch rate is inter-dispatch rate; scheduling delays can produce a lower observed rate or request bunching, which is not separately histogrammed. Local API load testing does not establish production capacity. Results vary by machine and runtime; the command does not guarantee any KPI target. These wall-clock measurements are distinct from theoretical complexity and structural storage evidence. In the latest recorded local run, all 3 runs had 0% failures, dispatch rates of 199.74, 199.92, and 199.15 req/s, and response throughputs of 199.58, 199.77, and 199.04 req/s. Thus the 200 req/s KPI remains **PARTIAL**: 0 of 3 runs reached 200 req/s for dispatch or response throughput; this is local evidence, not a production capacity claim.

Scripts: `npm test`, `npm run typecheck`, `npm run build`, `npm run demo:b1` through `npm run demo:b4`, and `npm run benchmark`.
